## 一、Bug 概述

**问题**：用户在 A agent 会话中发送消息、等待回复过程中切换到 B agent（甚至新建会话），再切回 A 时，A 的会话变成空白——刚发送的用户消息不见踪影，聊天历史里也查不到。

**影响面**：所有在 agent 生成回复过程中切换 agent 的用户。

**严重度**：致命（用户视角 = 消息丢失 + 会话消失）。

---

## 二、根因分析

消息并未真正丢失，但"看起来丢了"，且存在一个**真实的数据丢失窗口**。

### 2.1 数据丢失窗口

后端设计上"断连继续跑"：`task_tracker.py` 里每个 run 是独立的 asyncio task，HTTP 断开不会取消它。但**用户消息只在生成结束后才落库**（`SessionSaveHook` 挂在 `POST_RESPONSE` 阶段）。生成中途，消息的唯一副本是前端 `sessionStorage` 里的 `qwenpaw_pending_user_msg_*` 补丁缓存。

### 2.2 事故链路

1. **A 发消息，SSE 流式生成中**：`customFetch` POST `/console/chat`，同时把消息存进 `sessionStorage` 补丁缓存。后端 `post_console_chat` 调用 `get_or_create_chat` 建 chat，run 开始。**此刻消息没有落库。**

2. **切到 B —— 三件事同时坏掉**：
   - **(a) SDK 整体卸载重挂**：`setRefreshKey(+1)` 导致 `<AgentScopeRuntimeWebUI key={refreshKey}>` remount。A 的 SSE fetch 带 `signal: data.signal`，SDK 卸载时 abort → 前端流断开（后端还在跑）。
   - **(b) sessionApi 清空 A 的全部状态**：`setActiveAgent` 清 `sessionList`、`sessionResultCache`、`convertedSessionCache`、in-flight 请求。A 的会话从内存里蒸发。
   - **(c) 补丁缓存被静默丢弃**：pending 缓存还在 `sessionStorage` 里，但 `sessionApi` 的 epoch 机制让旧 A 时代的 `getSession` 结果全部作废。没有任何代码会在"切回 A"时主动去读它。

3. **在 B 新建会话**：`createSession` 造一个本地时间戳 id（`Date.now()-xxx`），`onSessionCreated` 里 `removeLastChatId(B)`。

4. **切回 A —— 恢复失败的三重门**：
   - **(a) 恢复目标可能拿到脏数据**：`getLastChatId(A)` 恢复 URL，但 `setLastChatId` 有个反直觉设计——**传入临时 id 会删掉已存的好 id**。如果 A 离开期间有临时 id 被误存，A 的真实 chat id 已被抹掉 → 恢复落空。
   - **(b) 就算 URL 恢复对，`getChat` 返回空**：后端从 session state 读消息。A 还在生成中 → `state` 里没有这轮 → `messages=[]`。reconnect 回放里只有 assistant 输出，没有用户那句话。
   - **(c) 补丁机制接不上**：`patchLastUserMessage` 本该补回用户消息，但要求 `loadPendingUserMessage(backendId)` 命中。如果 (a) 里 chat id 已丢，或 SDK remount 后 `currentSessionId` 是 undefined，补丁永远不会执行。

### 2.3 根因归纳

| # | 根因 | 位置 | 性质 |
|---|------|------|------|
| 1 | **用户消息延迟到生成结束才落库**，中途唯一副本是前端 sessionStorage 补丁 | `session_hook.py` POST_RESPONSE | 架构性数据风险 |
| 2 | **agent 切换 = 核弹式清空**：SDK remount 断 SSE + sessionApi 清全部缓存/列表/in-flight | `index.tsx:2570` + `sessionApi/index.ts:752` | 设计过于粗暴 |
| 3 | **`setLastChatId(临时id)` 反向删除好 id**，恢复目标被污染 | `agentStore.ts:155-161` | 逻辑陷阱 |
| 4 | **补丁缓存被动触发**，没有"切回时主动校验未落库消息"的补偿路径 | `sessionApi/index.ts:949` | 恢复链路缺口 |
| 5 | 生成中 `getChat` 返回 `messages=[]`，前端无"正在生成但历史为空"的占位态 | `api.py:768` | 体验缺陷 |

## 三、修复内容

本次实施了方案 1（根治）和方案 2（止血），共改动 7 个文件，新增 293 行。

### Fix 1: 后端立即落库用户消息【根治，对应根因 #1 #5】

**目标**：消除"生成中途消息没落库"的窗口。收到请求、run 开始前就把用户消息写入 chat.meta，任何时刻刷新/切换/断连历史都是完整的。

**文件**: `src/qwenpaw/app/routers/console.py`
- 新增 `_persist_pending_user_message()` 函数（约 65 行）
- 在 `post_console_chat` 的 `attach_or_start` **之前**调用
- 将用户消息写入 **chat.meta** 的 `pending_user_message` 字段（非 session state，避免 schema 冲突）
- 只持久化文本块（TextBlock）；媒体块（image/audio/video/file）被有意跳过——它们已作为文件落盘，前端从 pending cache 重新附加

**文件**: `src/qwenpaw/app/chats/api.py`
- `getChat` 在 `status == "running"` 时，读取 `chat.meta["pending_user_message"]` 并 `Msg.model_validate` 后合并到返回的 messages 末尾
- 去重：仅当 `memories` 末尾不是 user 角色时才 append（避免重复请求导致重复）
- `status == "idle"` 时跳过合并（消息已在 `agent.state.context` 中）

**文件**: `src/qwenpaw/app/chats/manager.py`
- `mark_chat_finished` 在 run 完成时，从 `chat.meta` 中 `pop("pending_user_message")`——turn 已完整持久化到 session state，占位不再需要

### Fix 2: `setLastChatId` 忽略临时 id 而非删除【止血，对应根因 #3】

**文件**: `console/src/stores/agentStore.ts`
- 原逻辑：传入临时 id 时 `delete remainingChatIds[agentId]`——删除已存的好 id
- 新逻辑：传入临时 id 时直接 `return`，保护已存的好 id

**文件**: `console/src/stores/agentStore.test.ts`
- 更新测试用例：从"临时 id 删除条目"改为"临时 id 保留条目"，并加注释说明这是回归测试

## 四、代码审查发现（DSH，2025-08-31）

对本次 7 个文件改动逐行审查，发现以下问题，按严重度排序。

### 4.1 【中风险·已修复】`_persist_pending_user_message` 绕过 ChatManager 锁，直接访问私有成员 `_repo`

**位置**: `src/qwenpaw/app/routers/console.py:397`

```python
await chat_manager._repo.upsert_chat(updated)
```

**问题**：`ChatManager` 的所有 meta 修改方法（`set_session_project_dirs`、`mark_chat_finished`、`update_chat_meta` 等）都在 `async with self._lock` 保护下做 read-modify-write。而 `_persist_pending_user_message` 直接访问 `chat_manager._repo.upsert_chat()`，**绕过了锁**。

**后果**：
- 并发场景下（如 reconnect 请求与新消息请求竞争同一 chat）存在 read-modify-write 竞态，可能丢失 project dirs 或 pending message 中的任一方对 meta 的修改。
- 与 `mark_chat_finished` 的写操作之间无互斥——如果 run 极快完成，`mark_chat_finished` pop pending 和 `_persist_pending_user_message` 写 pending 可能交错，导致 pending 被意外清除或残留。
- 访问私有成员 `_repo` 使代码与 `ChatManager` 内部实现强耦合，未来 repo 接口变更会直接破坏此处。

**建议**：在 `ChatManager` 上新增公开方法，走锁：

```python
async def set_pending_user_message(self, chat_id, msg_dump: dict) -> None:
    """在锁保护下写入 pending_user_message 到 chat.meta。"""
    async with self._lock:
        existing = await self._repo.get_chat(chat_id)
        if existing is None:
            return
        meta = dict(existing.meta or {})
        meta["pending_user_message"] = msg_dump
        updated = existing.model_copy(update={"meta": meta})
        await self._repo.upsert_chat(updated)
```

然后 `_persist_pending_user_message` 改为调用 `await workspace.chat_manager.set_pending_user_message(chat_id, msg.model_dump(mode="json"))`。

**现状评估**：当前 `post_console_chat` 中 `_persist_pending_project_dirs` 和 `_persist_pending_user_message` 是**串行先后调用**的，且都在 run 启动前，所以单请求内顺序无碍。竞态只在跨请求并发时出现，概率较低，但属于真实的正确性隐患。

> ✅ **已于 2025-08-31 修复**：在 `ChatManager` 新增公开方法 `set_pending_user_message(chat_id, msg_dump)`，走 `async with self._lock` 做 read-modify-write，与 `mark_chat_finished` / `set_session_project_dirs` 互斥。`console.py` 的 `_persist_pending_user_message` 不再直接访问 `_repo`，改为调用此方法。测试同步更新为验证公开方法调用参数。

### 4.2 【中风险·已修复】落库失败被 `logger.debug` 静默吞掉

**位置**: `src/qwenpaw/app/routers/console.py:405-409`

```python
except Exception:
    logger.debug(
        "failed to persist pending user message for chat=%s",
        chat_id[:30],
        exc_info=True,
    )
```

**问题**：生产环境日志级别通常为 `INFO`，`debug` 级别的异常不会输出。如果 pending 消息落库失败（如 DB 写入异常、序列化错误），bug 会**静默复现**——用户切回来还是看不到消息，但后端无任何告警，排查时无从下手。

**建议**：提升到 `logger.warning`，并带上 `chat_id` 全量（而非截断 30 字符）以便定位。

> ✅ **已于 2025-08-31 修复**：`logger.debug` 改为 `logger.warning`，`chat_id[:30]` 改为 `chat_id` 全量，并补充了 history may be incomplete on mid-run agent switch 说明。生产 INFO 级别下落库失败不再被静默吞掉。

```python
except Exception:
    logger.warning(
        "failed to persist pending user message for chat=%s; "
        "history may be incomplete on mid-run agent switch",
        chat_id,
        exc_info=True,
    )
```

### 4.3 【低风险】媒体消息不在 pending 中持久化，切换回来后历史缺失

**位置**: `src/qwenpaw/app/routers/console.py:375-378`

```python
# Media blocks (image/audio/video/file) are intentionally
# skipped: they are already persisted as files on disk and
# the frontend re-attaches them from the pending cache.
```

**问题**：只持久化 TextBlock，媒体块被跳过。注释说"前端从 pending cache 重新附加"，但这恰恰依赖前端 sessionStorage 补丁缓存——而本次修复的核心目标就是**让后端成为消息唯一可信源、退役前端补丁缓存**。此处形成逻辑矛盾：文本消息走后端兜底，媒体消息仍依赖前端补丁。

**后果**：切换回来后，如果前端补丁缓存已失效（如 sessionStorage 被清、epoch 机制作废），历史里媒体消息只剩文字部分，图片/音频/文件丢失。

**建议**：
- 短期：在遗留问题中明确记录此限制。
- 长期：媒体块也应序列化进 `pending_user_message`（Msg 的 content 支持 Block 列表，可 dump 媒体引用 URL）。

### 4.4 【低风险】`getChat` 合并去重逻辑偏弱

**位置**: `src/qwenpaw/app/chats/api.py:803-805`

```python
if not memories or memories[-1].role != "user":
    memories.append(pending_msg)
```

**问题**：去重仅检查 `memories` 末尾是否为 user 角色。
- 正常路径：context 末尾是 assistant（上一轮回复），pending 是新 user → 正确 append。✅
- 边界情况：若某种时序下 context 末尾恰好是 user（如重复请求/部分落库/重放），pending 会被跳过。此时如果两条 user 内容**不同**，新的 pending 消息会丢失。

**评估**：实际场景中，running 状态下 context 通常为空或以上一轮 assistant 结尾，末尾是 user 的情况极少。逻辑基本合理但不够健壮（未比较内容）。

**建议**：可改为比较末尾消息的内容指纹（如 role + content 文本哈希），更精确去重；或用 set/标志位记录 pending 是否已合并。

### 4.5 【极低风险】pending 残留：run 失败/被 kill 时不清除

**位置**: `src/qwenpaw/app/chats/manager.py`（`mark_chat_finished` 清除 pending）

**问题**：pending 仅在 `mark_chat_finished` 中清除。如果 run 因异常崩溃、被 `stop` 接口 kill、或进程重启而未走到 `mark_chat_finished`，`pending_user_message` 会永久留在 `chat.meta`。

**后果评估**：
- idle 状态 `getChat` 不合并 pending，所以**不影响显示正确性**。
- 但 meta 持续膨胀，若反复失败累积可能有多条残留（实际上每次写 pending 会覆盖，所以最多残留一条）。
- 下次正常发消息时新 pending 覆盖旧值，run 成功后清除，自愈。

**建议**：在 `post_console_chat` 非 reconnect 分支开头、写新 pending 前，无需额外清理（覆盖语义已足够）。如追求整洁可在 stop/cleanup 路径也 pop。

### 4.6 【代码风格】函数内 import

**位置**: `src/qwenpaw/app/routers/console.py:352`

```python
from agentscope.message import Msg, TextBlock
```

**问题**：`Msg`/`TextBlock` 在函数体内 import。文件其他位置（如 `_persist_pending_project_dirs` 内也 `from ...services.project_directory import ...`）有类似模式，推测是为避免循环导入或延迟加载。

**建议**：若非循环依赖，建议提到模块顶部；若是循环依赖，加注释说明原因。当前不阻塞，属风格项。

## 九、踩坑记录

### 9.1 第一版方案（已废弃）：session state 注入

最初尝试将 `pending_user_message` 写入 session state 的 `agent` key 下。结果导致新会话报错：

```
KeyError: "state_dict has neither 'state' nor 'memory' key"
```

**原因**：新会话的 session state 文件不存在，`load_session_state` 返回空 dict。注入 `pending_user_message` 后变成 `{"pending_user_message": ...}`，缺少 `state` key。`SessionLoadHook` 将其设为 `ctx.session_state`，`builder.build` 调用 `agent.load_state_dict({"pending_user_message": ...})` 直接崩溃。

**教训**：session state 的 `agent` key 有严格的 schema 要求（必须包含 `state` 或 `memory`）。任何额外字段都不能在 `state` 缺失的情况下单独存在。

**最终方案**：改用 `chat.meta` 存储 pending 消息。`chat.meta` 是自由格式的 dict，无 schema 约束，且 `SessionSaveHook` 不会触碰它。

### 9.2 `chat.meta` vs `session state` 的选择

`chat.meta` 被选中是因为：
- 自由格式 dict，无 schema 约束
- `SessionSaveHook` / `SessionLoadHook` 都不触碰它
- `ChatManager` 已有读写 meta 的基础设施
- `getChat` 已读取 `chat_spec.meta`，合并逻辑插入点自然

代价是：meta 的修改需走 manager 锁（见 §4.1 的偏差），且 `mark_chat_finished` 需手动清除。
